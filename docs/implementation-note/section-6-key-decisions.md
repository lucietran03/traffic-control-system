# 6. Key Implementation Decisions

*Table 9. Key implementation decisions*

| Decision | Reason | Implementation location | Consequence / trade-off | Evidence |
| --- | --- | --- | --- | --- |
| Local output authority | RC-09/PA-10: Central may send a high-level validated request (e.g. `REQUEST_FAULT_CLEAR`) but may never issue a raw gate/flasher/train-signal/traffic-signal actuation command — only the owning local controller ever calls its own driver functions, so one node's fault or a lost Qnet link can never cascade into another node's outputs. | `app/railway/src/rlx_fsm.c : rlx_fsm_on_fault_clear()` (the only effect `MSG_REQUEST_FAULT_CLEAR` can have — it re-checks live gate state itself rather than trusting Central); `app/intersection/src/lx_fsm.c : lx_fsm_check_fault_locked()` (line 60, `FAULT_SAFE` always wins even under an active `SUPERVISORY_CENTRAL_OVERRIDE`) | Central can be completely absent or lagging and every local controller keeps outputting a safe state; the trade-off is that Central's commands are only ever advisory and can be overridden or NACKed locally with no recourse but a fresh request. | `system_assumptions_tables.md` PA-10/RC-09; `docs/flow-diagrams/F-12-fault-safe-supervisory-override.md` |
| Direct railway pre-emption path | RC-10: the safety response to a railway fault (force train signal STOP, command gates closed) must not depend on Central connectivity or acknowledgement — reporting the fault to Central is a logically separate, independent action, not a precondition. | `app/railway/src/rlx_fsm.c : enter_fault()` (line 106) — synchronously calls `rlx_gate_command_close()`/`rlx_signal_show_fault()` and sets `state = RLX_FAULT` before anything else; only sets `fault_report_pending = 1` for a *different* thread (`rlx_main.c : on_pulse()` → `rlx_comm_send_fault_report()`) to drain later | The local safe-state transition can never be delayed by a MsgSend()/reply round-trip to C1, but Central's view of the fault is therefore eventually-consistent, not simultaneous with the physical change — an observer watching only Central's log can lag the real crossing state by up to one `on_pulse()` tick. | `docs/flow-diagrams/UC-06-respond-to-railway-equipment-fault.md` ("par" block: local safe state vs. independent report); exercised by `docs/test-plan/01-usecase-functional.md` TC-UC06-1 |
| Synchronous command replies | PA-12: every local controller must return `ACK`/`NACK` within 1 s of a Central command; if execution must wait for a safe phase boundary, it returns `ACK_ACCEPTED_PENDING` immediately and defers only the activation, not the acknowledgement. | `app/intersection/src/lx_fsm.c : lx_fsm_on_set_mode()` (`ACK` / `ACK_PENDING` / `NACK(OUT_OF_RANGE\|FAULT_ACTIVE)` branches, applied later at `lx_fsm_advance_phase_locked()`'s next `ALL_RED` boundary); mirrored by `lx_fsm_on_request_override()`/`lx_fsm_on_set_timing_profile()` | The operator gets timely feedback that a request was accepted for later application, but "ACK" never means "already in effect" — an assessor watching only the ACK line can be misled into thinking the change is immediate rather than deferred to the next safe boundary. | `system_assumptions_tables.md` PA-12; `docs/flow-diagrams/UC-07-configure-mode.md`; exercised by `docs/test-plan/04-timing-assumptions.md` DP-TIME-03 |
| `console_io_lock` outer, released around blocking reads | A second thread (the operator console) was added on top of a design where `mode_eng_lock` alone protected `c_mode_eng_t`; serialising terminal output additionally required a second lock (`console_io_lock`) for the 1 Hz `c_hmi_render()` table and command prompts. Fixed this session: the lock ordering must be fixed as `console_io_lock` always outer / `mode_eng_lock` always inner (never reversed) to rule out an AB-BA deadlock between the operator thread and the server thread's `on_pulse()`, and `console_io_lock` must be *released* around `read_long()`'s blocking `scanf("%ld", ...)` so an operator who pauses mid-keystroke cannot freeze the 1 Hz status render or delay an in-flight `on_pulse()` broadcast (e.g. the DP-01/DP-02 auto-switch) that only needs the same lock to print one log line. | `app/central/src/c_operator.c : read_long()` (lines 25-63, `unlock()` line 44 → blocking `scanf()` line 45 → `lock()` line 46) and `c_operator_reader_thread()`'s switch (lines 477-529, lock taken outer, before each `handle_*()`); ordering also documented and enforced in `app/central/src/c_main.c : on_pulse()` (lines 214-232) and `app/central/includes/c_operator.h` (lines 39-49) | Terminal output can never interleave mid-command (readable live demo), and the server thread is never starved waiting for a human to finish typing a number — but every `handle_*()` still serialises fully against `c_hmi_render()`, so a slow-typing operator can visibly delay the *next* second's status refresh by however long they take to press Enter, not just the read itself. | `docs/flow-diagrams/F-05-operator-console-dispatch.md`; exercised by `docs/test-plan/06-concurrency-race.md` TC-RACE-20 (operator commands racing server-thread `mode_eng_lock` traffic under full 9-controller load) |
| Heartbeat-carried full-state reconnect (PA-07/PA-08), no new IPC verb | UC-10 needed a way for a controller to detect 3 consecutive unacknowledged heartbeats and drop to `DEGRADED_LOCAL`, then resynchronise on reconnect with Central seeing the controller's complete current state — without adding a second wire message type or a two-phase resync handshake, since `heartbeat_payload_t` was already defined as the same struct as a full `MSG_STATUS` report. | `app/intersection/src/lx_fsm.c : lx_fsm_on_heartbeat_result()` (~L1232) / `app/railway/src/rlx_fsm.c : rlx_fsm_on_heartbeat_result()` (~L451) for the miss/ACK counting and `CENTRAL_CONNECTED ⇄ DEGRADED_LOCAL` transition; `ipc_msg.h` L139-141 `heartbeat_payload_t { status_report_payload_t summary; }`; Central-side independent detection in `app/central/src/c_watchdog_mon.c : c_watchdog_mon_tick()` | One fewer wire-visible step than `STATE_CHARTS.md` SC-05 models (`connectivity_state_t`'s `LINK_RESYNCHRONISING` value is defined but this implementation never sets it — `link_state` jumps `DEGRADED_LOCAL` → `CENTRAL_CONNECTED` on a single ACKed heartbeat); the trade-off is that Central and each Lx/RLx detect the same outage independently from their own bookkeeping and never exchange a shared "are we synced" acknowledgement beyond that one heartbeat. | `docs/flow-diagrams/UC-10-continue-local-operation-during-link-loss.md`; exercised by `docs/test-plan/01-usecase-functional.md` (UC-09 alt 5.1/2.1 cases, lines ~848-943, PA-07/PA-08) |
| Wiring `c_mode_eng_select_mode()` into a live DP-01/DP-02 auto-switch | The pure decision function `c_mode_eng_select_mode()` (schedule hour → `PEAK_FIXED`/`OFF_PEAK_SENSOR`) existed but, per `docs/test-plan/04-timing-assumptions.md`'s own recorded finding (DP-TIME-02), was never called with a real clock anywhere in `c_main.c`/`c_operator.c` — the auto-switch described by DP-02 was dead code prior to this session. It is now driven every 1 Hz tick, comparing the schedule-implied mode against `last_auto_mode` so it only broadcasts on an actual change, plus a `demo_hour`/`demo_hour_override_active` escape hatch (`c_operator.c` keys `d`/`a`) so a live demo is not at the mercy of the real wall clock. | `app/central/src/c_main.c : on_pulse()` (lines 176-220, `IPC_PULSE_HEARTBEAT_TICK` case) → `app/central/src/c_mode_eng.c : c_mode_eng_auto_check()` (declared `c_mode_eng.h` lines 140-151) → `c_comm_broadcast_set_mode()`; demo override in `app/central/src/c_operator.c : handle_demo_hour()`/`handle_resume_automatic()` | Six independent unicast `MSG_SET_MODE` sends fire per schedule boundary (not one broadcast frame), each subject to the same 1 s ACK/ACK_PENDING/NACK contract as a manual `m` command, and each Lx still only applies the change at its own next safe `ALL_RED` boundary — so the six controllers do not all switch mode at the identical instant. `peak_start_hour`/`peak_end_hour` remain placeholder values (`C_MODE_ENG_DEFAULT_PEAK_START_HOUR/_END_HOUR` = 6/9, `c_mode_eng.h` lines 38-49), not a specified boundary. | `docs/flow-diagrams/UC-07-configure-mode.md` path (b)/(b'); `docs/test-plan/04-timing-assumptions.md` DP-TIME-01/02/03 (DP-TIME-02 records the pre-fix gap this session closed; the doc text has not yet been updated to reflect the fix) |
| Mid-phase truncation of an already-running connector green on railway pre-emption | CC-01/CC-02 require that once a railway closure needs the toward-crossing movement suppressed, it is suppressed — but the pre-existing boundary-guard logic (`lx_fsm_advance_phase_locked()`'s `PHASE_ALL_RED_A_TO_B` case) only ever prevented a *new* connector green from starting during pre-emption; it never truncated one already in progress. Left unfixed, a connector green that started just before the crossing closed could run its full 30 s (`PEAK_FIXED`) or up to 40 s (`OFF_PEAK_SENSOR`/CC-03 drain-extended) duration — beyond the ~25 s adjacent-intersection clearance allowance RC-03's 45 s warning-to-arrival budget assumes (Appendix B4). | `app/intersection/src/lx_fsm.c : lx_fsm_on_phase_timer()`, `PHASE_CONNECTOR_GREEN` case (lines 1078-1119): a new check, run on *every* 100 ms tick (not modulo-gated like ordinary demand/extension checks), that once `supervisory == SUPERVISORY_RAILWAY_PREEMPTION && green_elapsed_ms >= LX_MIN_GREEN_MS`, clears `drain_active`/`drain_extending` and immediately calls `lx_fsm_advance_phase_locked()` to cut to YELLOW → ALL_RED instead of letting the phase run to its full/extended duration | The connector movement is guaranteed no more than its 8 s `LX_MIN_GREEN_MS` once pre-emption begins mid-phase (before: unbounded up to 40 s) — the trade-off is a slightly earlier-than-scheduled cutoff for vehicles already committed to the connector green, which is the intended safety bias (favouring the rail closure over completing an ordinary green cycle). | `docs/flow-diagrams/UC-05-manage-traffic-during-railway-closure.md` ("Moment 1 — crossing closes", alt branch "connector green already running (the fixed bug)"); no dedicated test-plan case currently isolates this exact mid-phase-entry scenario — `docs/test-plan/01-usecase-functional.md` TC-UC05-1..4 all begin pre-emption while L1 is still in `ARTERIAL_GREEN`, so this fix is a known test-plan coverage gap, not yet backed by a passed test run |
| Dynamic Qnet node resolution via `TRAFFIC_NODE_MAP` | The initial design implicitly assumed same-node messaging; deploying across 9 independent QNX VMs needs a way to route `MsgSend()` to the right physical node without hardcoding hostnames into the 3 project binaries or recompiling per deployment topology. | `app/shared/src/qnet_utils.c : resolve_node()` — lazily parsed exactly once per process via `pthread_once(&node_map_once, node_map_load)`; `node_map_load()` reads `getenv("TRAFFIC_NODE_MAP")` and reverse-maps each `suffix=node` pair through `suffix_to_id()` into `node_map[]`; `ipc_client_thread_main()` then builds either a local `traffic/<suffix>` path or a `/net/<node>/dev/name/global/traffic/<suffix>` path from that table, with a global→local retry if the cross-node `name_open()` fails | Zero source change or recompilation is needed to move a controller to a different VM — only the environment variable changes — but the map is parsed once per process lifetime (`pthread_once`), so a node relocated after process start requires a restart, and an unset/missing suffix silently falls back to same-node routing rather than failing loudly. | `docs/flow-diagrams/F-02-cross-node-name-resolution.md`; exercised by `docs/test-plan/07-cross-node-integration.md` (multi-VM `TRAFFIC_NODE_MAP` baseline cases) |
