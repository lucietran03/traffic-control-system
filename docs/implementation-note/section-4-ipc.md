# 4. Inter-Process Communication

## 4.1 Communication Topology

The system is a distributed set of independent QNX processes — one Central controller (`C1`), six intersection controllers (`L1`–`L6`), and three railway controllers (`RL1`–`RL3`) — that communicate exclusively over Qnet using native message-passing primitives. There is no shared memory, socket, or file-based IPC between nodes.

**Name attachment and discovery.** Every node calls `ipc_attach()` exactly once at startup (`app/shared/src/qnet_utils.c:204-238`), which wraps `name_attach()` to register a single channel under `traffic/<suffix>` (e.g. `traffic/c1`, `traffic/l3`, `traffic/rl2`; suffix table in `ipc_attach_name()`, `app/shared/src/qnet_utils.c:13-32`). The attach call requests `NAME_FLAG_ATTACH_GLOBAL` first, registering the name under `/dev/name/global/traffic/<suffix>` so it is visible to `name_open()` calls originating on other Qnet nodes; if the global name server is not running, `ipc_attach()` falls back to a local-namespace `name_attach(NULL, path, 0)` (`qnet_utils.c:230-233`). There are exactly 10 attach points, one per node — never one channel per message type. A peer wishing to send to a given node calls `name_open()` on that same `traffic/<suffix>` string; which physical/virtual Qnet node actually hosts a given suffix is resolved at runtime, not compile time, via the `TRAFFIC_NODE_MAP` environment variable (a comma-separated `<suffix>=<qnet-nodename>` list, parsed once and cached by `node_map_load()`/`resolve_node()`, `qnet_utils.c:102-158`). A suffix absent from the map — including the common case of the variable being unset entirely — resolves as "same node as the caller," identical to a plain `name_open("traffic/<suffix>", 0)`; a suffix present in the map instead opens `/net/<nodename>/dev/name/global/traffic/<suffix>`, with a fallback retry against the `/local/` namespace if the `/global/` open fails (`qnet_utils.c:165-202, 428-436`; see also `docs/flow-diagrams/F-02-cross-node-name-resolution.md`). This lets the same binaries run unmodified whether all nine controllers share one QNX image or are spread across separate VMs, per `app/shared/README.md`'s "Qnet attach-point names" section.

**Direct peer paths and supervisory authority.** Every cross-node verb is enumerated in `msg_type_t` (`app/shared/includes/ipc_msg.h:63-75`) and falls into three relationships:

- **C1 ↔ Lx** — Central is the only sender of `MSG_SET_MODE`, `MSG_SET_TIMING_PROFILE`, `MSG_REQUEST_OVERRIDE`, `MSG_RENEW_OVERRIDE`, `MSG_CANCEL_OVERRIDE`, and `MSG_REQUEST_FAULT_CLEAR` toward an intersection (all sent from `app/central/src/c_comm.c`, e.g. `c_comm_send_set_mode()` at `c_comm.c:119-131`, `c_comm_send_request_fault_clear()` at `c_comm.c:242-254`); Lx replies synchronously and separately sends `MSG_HEARTBEAT` back to `C1` (`app/intersection/src/lx_comm.c:40`). Central never sends a raw actuation command — every one of these verbs is a request that the target FSM independently validates and may accept, defer, or reject (Section 4.3).
- **C1 ↔ RLx** — Central sends only `MSG_REQUEST_FAULT_CLEAR` to a railway controller (same `c_comm_send_request_fault_clear()` function, generic over `controller_id_t target`, confirmed by its two call sites in `c_operator.c:handle_request_fault_clear()` offering either an Lx or an RLx target, `app/central/src/c_operator.c:366-391`); RLx independently sends `MSG_FAULT_REPORT` and `MSG_HEARTBEAT` to `C1` (`app/railway/src/rlx_comm.c:49, 80`). As with Lx, Central cannot command a gate, flasher, or train signal directly — `MSG_REQUEST_FAULT_CLEAR` only ever triggers `rlx_fsm_on_fault_clear()`, which re-checks the physical gate state itself before ACKing (RC-09; `docs/flow-diagrams/UC-06-respond-to-railway-equipment-fault.md`).
- **RLx → Lx** — one-way only. `rlx_comm_broadcast_crossing_status_if_changed()` (`app/railway/src/rlx_comm.c:146-171`) sends `MSG_CROSSING_STATUS` to both intersections adjacent to that crossing (the `ADJACENCY` table at `rlx_comm.c:108-113` fixes RL1↔{L1,L2}, RL2↔{L3,L4}, RL3↔{L5,L6}) and, via the same `send_crossing_status()` helper, to `C1` as well. A grep across `app/intersection/src/*.c` for any reference to a railway controller ID (`CTRL_RL1..3`) returns nothing: Lx never sends anything to RLx, and RLx never receives a command from an Lx. The safety authority for crossing protection stays entirely inside `rlx_fsm.c`.

**Synchronous request/reply behaviour and the 2-thread pattern.** Every cross-node exchange is one `MsgSend()`/`MsgReceive()`/`MsgReply()` round trip: the caller blocks on `MsgSend()` until the target's server thread replies. Because every node is simultaneously a client to some peers and a server to others (e.g. `C1` is a client sending `MSG_SET_MODE` to `L1` but a server receiving `MSG_HEARTBEAT` from the same `L1`), each node splits its IPC into two dedicated threads that never share work (`app/shared/README.md`, "Threading pattern"; `qnet_utils.h:59-74`): a **server thread** that only ever calls `ipc_attach()` once and then loops forever in `ipc_server_run()` (`qnet_utils.c:278-320`), never calling `MsgSend()`; and a **client thread** that loops forever in `ipc_client_thread_main()` (`qnet_utils.c:401-449`), draining a queue fed by the non-blocking `ipc_client_post()` (`qnet_utils.c:365-393`) and performing every outgoing `name_open()`/`MsgSend()`/`name_close()`. A third thread — the node's own `main()`/FSM — never calls `MsgSend()` itself; it only enqueues work via `ipc_client_post()`. This guarantees the thread that can be sent to (the server thread) never itself blocks sending to someone else, matching the deadlock-avoidance rule from `Lecture/Lecture02_Concurrent_Processes.pdf` slide 28 cited in `app/shared/README.md`.

**Pulses.** Each node arms one or more periodic/one-shot timers via `ipc_timer_arm()` (`qnet_utils.c:240-276`), which uses `SIGEV_PULSE` to deliver a pulse to the node's own channel rather than `SIGEV_THREAD`, avoiding a new OS thread per timer tick. Three application pulse codes are defined starting at `_PULSE_CODE_MINAVAIL` (`qnet_utils.h:80-85`): `IPC_PULSE_PHASE_TIMER` (Lx signal-phase stepping and demand-extension rechecks), `IPC_PULSE_HEARTBEAT_TICK` (every node, 1 Hz heartbeat cadence), and `IPC_PULSE_RAILWAY_WARNING` (RLx, drives the warning-to-arrival budget and doubles as the RLx FSM tick). A fourth code, `IPC_PULSE_RAILWAY_OCCUPANCY`, is declared but never armed (`docs/flow-diagrams/F-03-qnet-transport-internals.md`). All pulses and real messages land in the same `MsgReceive()` buffer inside `ipc_server_run()`; a pulse is identified by `rcvid == 0` and dispatched by `msg.hdr.code`, and is never replied to with `MsgReply()`.

**Heartbeat and ACK/NACK.** Every Lx and RLx sends `MSG_HEARTBEAT` to `C1` once per second (`lx_comm.c:40`, `rlx_comm.c:49`), carrying a `heartbeat_payload_t` that embeds the sender's full `status_report_payload_t`. Central replies with one of four `msg_result_t` values (`ipc_msg.h:78-88`): `RESULT_ACK` (accepted), `RESULT_ACK_PENDING` (accepted, activation deferred — PA-12), `RESULT_NACK` (rejected on safety/validity grounds, always paired with a `nack_reason_t`), or `RESULT_ERROR` (the request could not be processed at all — malformed or unrecognised verb — distinct from a validly parsed request that fails a safety check).

**Reconnection synchronisation (PA-07/PA-08).** Each Lx/RLx tracks its own link independently via `missed_heartbeat_acks` inside `lx_fsm_on_heartbeat_result()` / `rlx_fsm_on_heartbeat_result()`. Three consecutive unacknowledged (or send-failed) heartbeats transition `connectivity_state_t` from `LINK_CENTRAL_CONNECTED` to `LINK_DEGRADED_LOCAL` (PA-07). The very next heartbeat that does receive `RESULT_ACK` transitions it straight back to `LINK_CENTRAL_CONNECTED` (PA-08) — there is no separate resynchronisation message, because `heartbeat_payload_t` already carries the complete `status_report_payload_t` snapshot on every tick, so the first ACKed heartbeat after an outage already satisfies PA-08's "send complete current state on reconnect" requirement for free. `connectivity_state_t` does define a third value, `LINK_RESYNCHRONISING` (`sys_types.h:94-99`), matching `STATE_CHARTS.md` SC-05, but this implementation never sets it as an observable window; the transition is direct, one fewer wire-visible step than SC-05/SD-08 illustrate. Central detects the same event independently and asymmetrically, from its own `c_watchdog_mon_tick()` bookkeeping (`marked_unavailable`), never by reading the peer's `link_state` field — see `docs/flow-diagrams/UC-10-continue-local-operation-during-link-loss.md` for the full trace.

## 4.3 Message Validation and Failure Handling

**Wire-format contract.** Both `ipc_request_t` and `ipc_reply_t` begin with `msg_header_t` (`ipc_msg.h:51-59`), a struct deliberately laid out to mirror QNX's `struct _pulse` field-for-field rather than including the real type — `sival_ptr` differs in size between 32-bit and 64-bit targets, so using the genuine `struct _pulse` would corrupt the layout on whichever architecture didn't define it. This matters because `MsgReceive()` writes both real messages and kernel/timer pulses into the same buffer (`ipc_server_run()`, `qnet_utils.c:278-320`); when `rcvid == 0`, `hdr.code`/`hdr.scoid` must still read correctly as pulse fields. Beyond the header, every payload field that crosses a node boundary is a fixed-width type (`uint8_t`/`uint32_t`/`uint64_t`), never a plain C enum — a C enum's underlying storage width is implementation-defined, and C1/Lx/RLx are separate Qnet nodes that may run on different target architectures. Enum types (`msg_type_t`, `msg_result_t`, `operating_mode_t`, etc.) are still used as named constants on both sides, but the struct field itself is always declared as an explicit-width integer with a comment stating which enum it holds.

**Verb-based dispatch.** There is one channel per node, not one per message; the receiving `on_request()` handler (e.g. `c_main.c`'s `switch ((msg_type_t)req->verb)`, or the equivalent in `lx_main.c`/`rlx_main.c`) reads `ipc_request_t.verb` to decide which FSM entry point to call. This is a distinct field from `ipc_request_t.hdr.type`, which belongs to the pulse-compatible header and is used only for `_IO_CONNECT`/`_IO_*` detection inside `ipc_server_run()`; `ipc_client_post()` explicitly zeroes `hdr.type`/`hdr.subtype` before enqueueing (`qnet_utils.c:384-385`) so the two dispatch mechanisms can never collide.

**Range/validation checks in the receiving FSM.** Every command-carrying verb is re-validated by the target's own FSM, not trusted from the wire, per PA-09's "reject unsafe requests with NACK, never silently apply." Two concrete, recently-audited examples:

- `lx_fsm_on_set_mode()` (`app/intersection/src/lx_fsm.c:692` onward) checks `payload->mode != MODE_PEAK_FIXED && payload->mode != MODE_OFF_PEAK_SENSOR` and replies `RESULT_NACK`/`NACK_REASON_OUT_OF_RANGE` for anything outside that range. The inline comment records this as a compliance-audit fix: before the check existed, every runtime test was an `if (mode == MODE_PEAK_FIXED) {...} else {...}`, so an out-of-range wire value would have silently behaved like `OFF_PEAK_SENSOR` instead of being rejected. `c_operator.c` itself only ever offers 0/1, so the NACK path is unreachable from the operator console today — but `lx_fsm.c`, not the console, is the documented authoritative validator, since the wire contract gives no guarantee the sender is a well-behaved operator.
- `lx_fsm_on_request_override()` (`app/intersection/src/lx_fsm.c`, ~line 755) checks `payload->target_movement != OVERRIDE_MOVEMENT_ARTERIAL && payload->target_movement != OVERRIDE_MOVEMENT_CONNECTOR` and NACKs with `NACK_REASON_OUT_OF_RANGE` if it fails — the same defense-in-depth rationale, since every call site elsewhere only ever tests `== OVERRIDE_MOVEMENT_CONNECTOR`, so an invalid value would otherwise have silently defaulted to `OVERRIDE_MOVEMENT_ARTERIAL`. The same function also enforces PA-11's duration bound directly: `payload->duration_ms == 0 || payload->duration_ms > LX_OVERRIDE_DURATION_CAP_MS` → `NACK_REASON_INVALID_DURATION`, and rejects a second `MSG_REQUEST_OVERRIDE` while one is already `SUPERVISORY_CENTRAL_OVERRIDE` (a request already in flight must go through `MSG_RENEW_OVERRIDE` instead).

Similarly, `rlx_fsm_on_fault_clear()` (`app/railway/src/rlx_fsm.c:297-326`) never trusts that a repair has actually happened just because Central asked: it first NACKs with `NACK_REASON_UNKNOWN_TARGET` if the crossing is not currently in `RLX_FAULT` at all, then, if it is faulted, performs a live `gates_confirmed_open()` re-check (explicitly not a value cached earlier in the request) and only replies `RESULT_ACK` — clearing `faults` and stale occupancy-window bookkeeping — if the gates are physically confirmed open; otherwise `RESULT_NACK`/`NACK_REASON_FAULT_ACTIVE`, retaining the safe fault state (RC-09/RC-10: "Central's request never bypasses live verification").

**NACK reason codes.** `nack_reason_t` (`sys_types.h:165-174`) enumerates: `NACK_REASON_NONE` (no rejection), `NACK_REASON_INVALID_DURATION` (PA-11 — override duration missing, non-positive, or over the 5-minute cap), `NACK_REASON_RAILWAY_CONFLICT` (CC-02 — requested movement is toward a non-open crossing), `NACK_REASON_PEDESTRIAN_ACTIVE` (UC-08/SD-07 — pedestrian clearance active and cannot be safely deferred), `NACK_REASON_FAULT_ACTIVE` (PA-09 — a local fault means the request would violate a safety invariant), `NACK_REASON_STALE_OR_UNSAFE_PROFILE` (UC-03 Alt 3.1/TL-01 — offset or timing violates a local safety bound), `NACK_REASON_OUT_OF_RANGE` (used both for genuinely out-of-range wire values, per the two examples above, and — for lack of a dedicated code — for "an override is already in flight, use RENEW_OVERRIDE instead"), and `NACK_REASON_UNKNOWN_TARGET`.

**PA-12 response deadline.** The design requires every command to receive `RESULT_ACK`/`RESULT_NACK`/`RESULT_ACK_PENDING` within 1 second (documented against SD-07's override-request path: "ACK is returned within 1 s, while only activation is deferred"). No explicit software timer, `TimerTimeout()`, or watchdog enforces this deadline anywhere in `qnet_utils.c` — `ipc_client_thread_main()` calls `MsgSend()` directly with no timeout wrapper, and it blocks until the peer's `MsgReply()`. The deadline is instead satisfied structurally: `ipc_server_run()`'s `on_request()` callback contract explicitly forbids blocking (no `MsgSend()`, no waiting on the client queue) inside a request handler, so every FSM validation runs synchronously and returns in the same `MsgReceive()`/`MsgReply()` round trip with no I/O wait in between, leaving only OS scheduling and Qnet transport latency between request and reply. `docs/test-plan/04-timing-assumptions.md` (test case PA-TIME-06) records this explicitly and treats PA-12 compliance as something verified by manual/measured round-trip latency rather than an enforced code-level deadline. `RESULT_ACK_PENDING` is the mechanism for cases where the underlying action (e.g. activating an override) must wait for something else (pedestrian clearance) to finish — the reply itself is still immediate; only the request's effect is deferred.

**Heartbeat loss and reconnection** are covered in full in Section 4.1 (PA-07's 3-consecutive-miss detection and PA-08's reconnection state-sync via the next ACKed heartbeat) and are not repeated here.

**RC-10 — railway safety response never waits for Central.** When `rlx_fsm.c`'s `enter_fault()` detects an unverifiable gate condition, it performs the local safe-state actions (forcing/holding train signals to `STOP`, commanding and holding documented safe gate/flasher outputs) synchronously and immediately, before anything is sent over Qnet. Reporting the fault (`MSG_FAULT_REPORT` to C1) is handled by a different code path — `enter_fault()` only sets a flag (`fault_report_pending`), which a separate iteration of the node's own pulse-driven loop later drains and turns into an actual `rlx_comm_send_fault_report()` call. Neither branch waits on the other, and the local safety response has already taken effect by the time the report is even queued — the contained fault handling proceeds locally and in parallel with reporting, never gated on Central being reachable (`docs/flow-diagrams/UC-06-respond-to-railway-equipment-fault.md`).
