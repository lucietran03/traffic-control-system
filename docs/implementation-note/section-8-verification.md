# 8. Verification and Test Results

## 8.1 Test Environment and Method

Testing was executed by the team on a **real multi-VM QNX deployment connected via Qnet** — environment **(C)** in `docs/test-plan/`'s own environment tagging (multiple physical/virtual QNX targets, `TRAFFIC_NODE_MAP` addressing) — following the setup procedure in `docs/QNX_DEPLOYMENT_RUN_GUIDE.md` (network/Qnet setup, binary transfer, `TRAFFIC_NODE_MAP` configuration, launch order).

**Case count**: `docs/test-plan/` contains **232 unique test-case IDs** across the seven `01-*.md` through `07-*.md` files (45 + 43 + 48 + 32 + 24 + 21 + 19 — verified by extracting every `### TC-...`/`#### TC-XNODE-...` heading per file and de-duplicating; no repeated IDs found in any file). A naive heading count on file 01 gives 46, not 45, because `01-usecase-functional.md`'s own "Cách đọc một test case" section (§2) contains a fenced-code-block **format template** whose placeholder heading also matches a loose `### TC-...` pattern — it is not a real case (renamed to `TC-EXAMPLE-N` to prevent this miscount going forward). This is a **different number** from `tools/test-automation/cases/*.json`'s **227 total entries** — that JSON corpus is a narrower, keyboard-scriptable subset the automation runner can drive as subprocesses (it explicitly skips anything needing environment (C)/(D) or a debugger, per its own README), not a re-statement of the full test-plan's case count. The two numbers should not be compared directly.

No case is marked Pass without either a real keyboard-driven run with a verified precondition, or an explicit, test-plan-defined code-review fallback; no case's status was inferred from source code or from the test-plan's own "expected result" text alone.

Timing figures in Section 8.3 were derived from whichever method each row actually supports — see the **Method** column of Table 11 for the specific instrument used per row (they are not uniformly "`central_log.txt` timestamp diff": Lx/RLx print to their own local console only, never to `central_log.txt`, which is Central-only and only logs edge-triggered events, not every heartbeat/phase transition — see Table 11's notes).

In addition to this real multi-VM execution, two static verification methods were used earlier in development and remain part of the evidence trail:
- `make check-syntax` — a host-`gcc`/`clang` `-fsyntax-only` pass over all three projects' sources (`Makefile` lines 199-223), explicitly documented as "NOT a QNX build." It catches C syntax errors, missing includes, and type mismatches, and was kept green throughout development, but it does not by itself validate QNX runtime behaviour — that validation is what the real multi-VM run above provides.
- A multi-agent spec-compliance audit conducted earlier in this project's development, cross-referencing the implemented `app/` source against `usecase.md`, `SEQUENCE_DIAGRAMS.md`, `STATE_CHARTS.md`, and `system_assumptions_tables.md`. This found and fixed several real defects by code inspection (see Table 12) *before* the full run reported here, so the run below already reflects the post-fix codebase.
