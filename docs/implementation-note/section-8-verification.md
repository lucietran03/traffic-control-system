# 8. Verification and Test Results

## 8.1 Test Environment and Method

Three distinct verification methods were used while preparing this submission. The first two require a real QNX target and were **not executed inside this documentation-writing session** (no QNX SDP toolchain or running QNX VM was available in this environment); the third was executed and its findings are cited directly below and in Table 12.

**(a) Manual keyboard injection across multiple QNX VMs/targets (Qnet).** The team's intended, primary test method for the full 227-case plan in `docs/test-plan/` is to deploy the compiled `c_main`, `lx_main`, and `rlx_main` binaries across QNX Virtual Machines connected via Qnet, following `docs/QNX_DEPLOYMENT_RUN_GUIDE.md` (network/Qnet setup in section 1, binary transfer and `TRAFFIC_NODE_MAP` addressing in section 2, single-workstation vs. multi-PC topologies in section 3). Each `docs/test-plan/0N-*.md` file tags every case with an environment letter — **(A)** single node, **(B)** multiple nodes on one machine (no `TRAFFIC_NODE_MAP` needed), or **(C)** multiple physical/virtual machines over real Qnet (`TRAFFIC_NODE_MAP` required) — and testers press the documented keys on `lx_sensor.c`/`rlx_sensor.c`/`c_operator.c`'s stdin readers and compare console/log output against the expected result written in the case. This method is the only one that can exercise genuine cross-VM Qnet behaviour (environment (C), 19 cases in `07-cross-node-integration.md`) and true multi-day/real-wall-clock scenarios. **It requires the assessor's or team's own QNX VM environment to actually run — no such environment was available in this session, so no case using this method has an observed result to report here.**

**(b) Scripted-keystroke automation (`tools/test-automation/`).** For environments **(A)** and **(B)** only (same-machine, no distinct Qnet-routed VMs required), the team built a real, working automation harness: `tools/test-automation/runner.py` launches the actual compiled binaries as subprocesses, sends the exact keystrokes from a JSON case file at scripted millisecond offsets (respecting each program's real stdin read mode — single-character `scanf(" %c", ...)` for the sensor readers vs. newline-terminated `scanf("%ld", ...)` for `c_operator.c`'s numeric prompts), and checks the resulting output against per-node regex patterns within a time window (`checks[].within_ms`/`after_ms`), including a `repeat: N` mode for the concurrency/race cases in `06-concurrency-race.md` that call for N≥5–10 repetitions. Cases that need environment (C), the not-yet-built `test_client` protocol tool (environment (D)), a debugger, or genuine human visual/stopwatch judgement are marked `"skip": true` with a reason and reported as `SKIP`, never faked as a pass. This tool is real and functional, but it still requires the real QNX-built binaries (`build/bin/{c_main,lx_main,rlx_main}`) to run against; **it has not been run against a QNX build in this session** (no QNX SDP toolchain is present on this development machine), so no automated pass/fail results exist yet either.

**(c) Static/code-level verification (performed and evidenced in this repository).** Two forms of static verification were actually carried out on this development machine, without a QNX target:
- `make check-syntax` — a host-`gcc`/`clang` `-fsyntax-only` pass over all three projects' sources (`Makefile` lines 199-223), explicitly documented as "NOT a QNX build" — it catches C syntax errors, missing includes, and type mismatches, but cannot validate QNX-specific runtime behaviour (`MsgSend`/`MsgReceive` semantics, channel/pulse delivery, resource-manager behaviour, real timing).
- A multi-agent spec-compliance audit conducted earlier in this project's development, cross-referencing the implemented `app/` source against `usecase.md`, `SEQUENCE_DIAGRAMS.md`, `STATE_CHARTS.md`, and `system_assumptions_tables.md`. This audit is real engineering work with a real artifact trail (see commit `850ecb5` and `a1bacb0`) and found and fixed several genuine defects by code inspection — these are cited honestly in Table 12 as "found/fixed by code audit, not exercised on hardware," which is a materially different and weaker form of evidence than an executed test, and is presented as such throughout this section.

No claim of "Pass" appears anywhere in Section 8 unless it is qualified as a configured/derived design value or a code-audit finding; every result that would require executing the compiled system on a real or simulated QNX target is marked **"Not yet executed — pending run on QNX target."**
