**1.2 System Assumptions** << Document any assumptions you made about how the system will operate. You must explicitly state and justify the assumptions used for timing, traffic coordination, and congestion control. You should also state any assumptions regarding differences in traffic demand and priority between roads R1-R5. >> To bridge the gap between abstract requirements and concrete software implementation, specific operational parameters must be established. The following tables outline the foundational parameters guiding the system architecture, ensuring realistic traffic flow and reliable interprocess communication.

**1.2.2 Traffic demand and road priority assumptions (DP-xx)**

Peak periods are 07:00–09:00 and 16:00–19:00, while all other operating periods are classified as Off-Peak for road-traffic control purposes.                                                                                                           | The specification refers to Peak and Off-Peak operation but does not define their exact time boundaries. | DP-03  | Each road is assigned a static base traffic priority from 1–5, where 5 represents the highest normal traffic priority. | DP-04  | R1 and R2 are treated as primary arterial roads, while R3–R5 are treated as cross-network connector roads.                                                                                                                                                                                    | Based on the adopted project topology, R1 connects I1–I3–I5 and R2 connects I2–I4–I6, while R3–R5 connect corresponding intersections across the railway corridor. The specification explicitly suggests using distances between intersections and railway crossings to determine timing requirements and prevent traffic backing up.                                     | R4 may receive stronger congestion/coordination intervention than another road with similar demand even though R1/R2 retain higher normal base priority. | DP-07  | Lower-priority roads must receive eventual traffic service and cannot be indefinitely blocked solely because higher-priority traffic remains present.                                                                                                                                         | A static priority hierarchy without a fairness constraint could continuously favour R1/R2 and starve lower-priority approaches. | ASM-TIM-02 | Yellow (Amber) Time: Set to 4.0 s for all vehicle approaches.                   | Calculated using kinematic stopping formula Y = tr + v / (2a) (1.0 s + (16.7 m/s) / (2 \* 3.0 m/s^2) = 3.78 s ≈ 4.0 s) for 60 km/h traffic to completely eliminate the driver Dilemma Zone.                     | Controller state machine implements an explicit STATE_YELLOW with a 4.0 s one-shot timer before triggering red.                                                 |
| ASM-TIM-03 | All-Red Clearance: Set to 2.0 s for all phase transitions.                      | Allows a vehicle entering on the last moment of yellow to fully clear the 22 m intersection conflict box (R_all = (22 + 5) / 16.7 = 1.62 s ≈ 2.0 s) before cross-traffic gets green, preventing T-bone crashes. | Controller state machine includes a mandatory STATE_ALL_RED where all signal outputs are held RED for 2.0 s.                                                    |

**1.2.7. Pedestrian, Sensing and Abnormal Operation Assumptions (PA-xx)**

\*\* \*\* \*\* \*\* The handling of real-time inputs and edge cases is critical to maintaining a robust distributed network. To ensure localized safety and predictable failure states, the following assumptions define how pedestrian interactions, sensor data, and unexpected system faults are processed independently of standard traffic flow. |

Pedestrian Operation

| **_ID_**  | **_Assumption_**                                                                                                          | **_Justification_**                                                                                                                                                              | **_Design Implication_**                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **PA-01** | Pedestrian requests remain active and serviceable across both Peak and Off-Peak operating modes.                          | Disabling requests during peak hours would trap pedestrians. The Peak/Off-Peak distinction is therefore applied to vehicle-control strategy rather than pedestrian availability. | Peak fixed-timing routines must inherently account for and service pedestrian _WALK_ phases.                            |
| **PA-02** | Pedestrian button presses create latched requests; repeated presses do not extend service time.                           | Prevents redundant queuing and ensures maximum vehicle wait times are not infinitely extended by pedestrians.                                                                    | The controller stores a Boolean _pending_ flag that clears only after the _WALK_ phase concludes.                       |
| **PA-03** | Pedestrian requests are serviced at the next valid phase transition, never abruptly interrupting an active vehicle green. | Immediate interruption violates minimum vehicle timing and introduces severe collision risks.                                                                                    | Pedestrian inputs alter future state queueing, not the immediate actuator outputs.                                      |
| **PA-04** | A WALK signal activates strictly when all conflicting vehicle movements are in an All-Red or Red state.                   | Eliminates ambiguity regarding when a crosswalk is safe to enter.                                                                                                                | The state chart will feature strict conflict matrices linking vehicle and pedestrian signals.                           |
| **PA-05** | Pedestrian requests blocked by a railway preemption event remain latched and are prioritized during recovery.             | Ensure pedestrians do not lose their place in the service queue due to train interference.                                                                                       | Upon exiting the _TRACK_BLOCKED_ state, controllers check for pending pedestrian flags before resuming baseline cycles. |

Vehicle and Pedestrian Sensing

| **_ID_**  | **_Assumption_**                                                                                                     | **_Justification_**                                                                                       | **_Design Implication_**                                                                                                                         |
| --------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **PA-06** | One logical vehicle-presence detector is utilized per road approach, covering all lanes collectively.                | Approach-level sensing is sufficient for phase actuation without unnecessarily burdening the I/O count.   | Four logical inputs are processed per intersection; detection identifies general demand, not specific lane usage.                                |
| **PA-07** | A vehicle detector reports **presence/no presence**, rather than an exact vehicle count or queue length.             | Advanced queue measurement exceeds the required scope of this proof-of-concept.                           | Sensor logic acts as a Boolean trigger for phase extensions or skips.                                                                            |
| **PA-08** | Sensor data monitors congestion during Peak periods but actively influences phase selection during Off-Peak periods. | Fixed timing handles dense traffic best, while low traffic benefits from immediate sensor responsiveness. | The local control loops apply different weights to sensor flags depending on the active time-of-day mode.                                        |
| **PA-09** | Pedestrian demand relies strictly on push-button actuation; passive automated detection is omitted.                  | Push-buttons provide deterministic inputs ideal for demonstrating basic real-time responsiveness.         | The local controller does not infer pedestrian demand automatically. A pedestrian must generate a request through the corresponding push button. |

Abnormal / Failure Operation

| **_ID_**  | **_Assumption_**                                                                                                                  | **_Justification_**                                                                                                        | **_Design Implication_**                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **PA-10** | Upon losing communication with the central controller, a local controller locks into its last known valid sequence configuration. | Fulfills the requirement that nodes continue operating safely without unpredictably altering their timing behavior.        | Local controllers (I1-I6) store their active configuration locally and run it autonomously until a heartbeat is re-established. |
| **PA-11** | A failed vehicle detector triggers a localized fallback to fixed timing for its specific approach.                                | Treating a dead sensor as “no vehicles” would permanently starve that approach of service.                                 | The controller will enforce maximum green times for the affected approach to guarantee service.                                 |
| **PA-12** | Faulty pedestrian buttons are ignored for safety-critical phase transitions but flagged for maintenance.                          | A short-circuited button should not continuously force the intersection into pedestrian service loops.                     | Continuous button holds exceeding a reasonable threshold are logged as errors and bypassed in the phase queue.                  |
| **PA-13** | Unrecognized or corrupted commands from the central node are strictly rejected.                                                   | Malformed data must not force the intersection into an undefined or conflicting hardware state.                            | Incoming IPC messages undergo strict validation; invalid packets are dropped and an error status is returned.                   |
| **PA-14** | Following a network recovery, local nodes push their status to the center before accepting new synchronization commands.          | State drift during a disconnect means the central controller's view is stale; immediate blind commands could be dangerous. | A sync handshake protocol forces a local-to-central state update prior to resuming remote coordination.                         |
| **PA-15** | A central controller failure does not trigger an intersection all-red state; intersections maintain autonomous cycling.           | A single-point monitoring failure should not intentionally gridlock the entire road network.                               | The system degrades gracefully; coordination may drift, but local intersection safety is preserved.                             |
